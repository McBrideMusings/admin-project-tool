# Guards are named preconditions referenced from `requires` on actions and targets

An action (or a multi-target child target) may declare a `requires = ["<guard-name>", ...]` list. Each name resolves through one shared registry that contains both Python-defined built-in **Guards** (`admin_lib/guards.py`) and TOML-defined user **Guards** (`[guards.<name>]` tables). Before the action's `run` fires, each named Guard is invoked in order, fail-fast; on failure, the runtime prints the Guard's diagnostic message and exits non-zero. There is no dedicated `[git_gate]` table — the existing two checks (clean working tree, branch pushed to origin) ship as the built-in Guards `git-clean` and `git-pushed`, opted into per action/target by name.

**Why.** The first cut shipped `[git_gate]` as a flat table listing top-level commands to gate (`commands = ["preview", "staging", "deploy"]`). On Reddit Poker that worked for a day, then immediately broke down: `[actions.preview]` is `kind = "multi-target"` with four targets (`cf`, `mainframe`, `devvit`, `migrate`), and only three of them should be gated. `devvit` deploys to a dev subreddit where iterating with a dirty tree is fine; the others touch production-adjacent infrastructure where it isn't. Command-level granularity couldn't express that, and the property was sitting on the wrong concept anyway — commands are pure routing ([ADR-0003](./0003-commands-are-pure-routing.md)). The "needs a clean repo" property belongs on the thing that *does* the deploy (the action/target), not on the menu entry that invokes it.

Generalizing from "git gate" to "arbitrary precondition" also fell out for free: once the gate is a named, addressable thing on an action, there's no reason it can't be any shell expression with an exit code — and giving users a TOML escape hatch (`[guards.no-untested-migration] run = "..."`) costs almost nothing on top of the built-in registry.

**Considered and rejected.**

- **Keep `[git_gate].commands`, add a parallel `[git_gate].targets = ["preview.cf", ...]`.** Solves the granularity problem mechanically but spreads the gating decision far from the thing being gated. Every new multi-target child is a silent gap until someone updates `[git_gate]`. The gate table also has to enumerate the structure of every action it touches — a leaky coupling that gets worse with every new target.
- **Inline pair on every action/target** (`requires = [{ run = "...", fail = "..." }, ...]`). Local, but repeats verbatim across every gated target — the same git-clean expression copied into a dozen places, with no way to share or audit consistency. Mistyping one is a silent gap.
- **Hybrid: keep `[git_gate]` as a privileged preset, add `[guards]` for everything else.** Two ways to define the same concept. The preset gets configuration knobs (`require_clean`, `require_pushed`) while user-defined guards don't, which is asymmetric. Removed; the knobs collapse into "reference the guard or don't."
- **Per-target only (no parent default).** Forces every gated child to repeat `requires = ["git-clean", "git-pushed"]`. A new target added six months later without `requires` is silently ungated — the dangerous failure mode for deploy work. Parent-default-with-child-override flips this so the dangerous failure mode is the harmless one: a forgotten override produces a loud false alarm, not a silent skip.

**Consequences.**

- **Multi-target inheritance is replace-not-merge.** A child's `requires`, if present, fully replaces the parent's. `requires = []` on a child is the explicit opt-out. Merging across the two levels was considered and rejected — the predictability cost of "does this child *add* to the parent or replace it?" outweighed any DRY benefit.
- **Asymmetric authoring is deliberate.** Built-in Guards are Python so they can produce dynamic diagnostics (`"branch 'X' has unpushed commits — push first: git push origin X"`). User-defined Guards are TOML with a static `fail` string. Both reference the same `requires = [name]` syntax at the call site. If a user-defined Guard outgrows TOML, it gets promoted to Python via PR.
- **No backwards-compatibility for `[git_gate]`.** The table is deleted in the same change that introduces `[guards]`. Reddit Poker is the only consumer; its migration is part of the rollout. A deprecated alias was considered and rejected — one consumer doesn't justify the dual-mechanism debt.
- **Audit-time validation lands in `admin-gen`.** Every name in a `requires` list must resolve to either a Python-registered Guard or a `[guards.<name>]` table; otherwise the generator errors with the missing name and the list of known Guards.
- **Guards do not compose with each other.** A Guard cannot list its own `requires`. Keeps the resolution model trivial — a flat lookup, never a graph.

- **One Guard also runs as an always-on preflight, by exception.** The model above is "a Guard runs only when an action's `requires` names it." `deps-fresh` (node/bun workspace integrity — a `workspace:*` dependency declared but not linked into `node_modules`) breaks that: besides being referenceable in `requires` like any built-in, it also runs unconditionally before *every* command via `run_global_preflight` (in `admin_lib/guards.py`), no annotation needed. The carve-out is deliberate and narrow: the git Guards gate a *specific action* (this deploy needs a clean tree), so opt-in-per-action is right; `deps-fresh` guards the interpreter's own ability to run project code *at all* (a stale install makes builds/dev fail with an opaque bundler error), so requiring every project to annotate every build/dev/deploy action would just be a footgun — the dangerous failure mode (a forgotten annotation) would be the silent one. Always-on with a small exempt set (`logs`, `kill` — the verbs you need to diagnose or recover) keeps the dangerous mode loud. The always-on checks live in `_PREFLIGHT_CHECKS` (the preflight analogue of `GUARDS_BUILTIN`); adding another is appending to that tuple, and the bar for doing so is the same "guards the tool's ability to run, not one action" test. The preflight is fail-open — a bug or unusual manifest degrades to a no-op pass, never a crash or a block.

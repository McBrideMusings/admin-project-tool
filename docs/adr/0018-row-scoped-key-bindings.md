# ADR-0018: Dashboard key bindings are declared per row kind, and `enter` is an ordinary binding

`admin.toml` may carry a top-level `[keys.<row-kind>]` table per bindable Row kind (`bead`, `issue`, `branch`, `pr`, `commit`, `stash`, and the Work tab's `command`, `commandTarget`, `worker`), mapping a key to the name of a Command in the same manifest. The dashboard consults `keys[rowKind][key]` before its own key switch; an unbound (key, row kind) pair falls through to the built-in behavior unchanged. `enter` gets no special treatment — overriding what Enter does on a bead is the same mechanism as adding a new key on a bead.

A reserved set is never bindable: `q`, `ctrl+c`, `esc`, `tab`, `shift+tab`, the arrows, `j`, `k`, `1`–`4`, `/`. Shadowing a built-in is reported by `admin check`, not blocked.

A non-workflow bound command receives its row through the environment — `ADMIN_ROW_KIND`, `ADMIN_ROW_ID`, `ADMIN_ROW_URL` — rather than as arguments. On a Work row, `ADMIN_ROW_ID` is the live-work id the row's run is keyed on (the command name, `<command>:<target>`, or the worker's id), which is also what a reload loop records as its owner — so a Work-row key bound to a `kind = "server-reload"` command reloads that row's loop and no other. A bound command resolving to a single-step `kind="workflow"` action with `over = "row"` dispatches over the cursor row alone; every other bound command also acts on the cursor row alone.

`[keys.<row-kind>]` merges per key, not per whole table, unlike every other raw archetype table (`[apple]`, `[deploy]`, ...) — the one exception in `internal/archetype/merge.go`'s `mergeRowKeys`. An archetype's `[keys.bead] enter = "implement"` and a project's `[keys.bead] o = "open-bead"` both survive; a project override does not silently drop the archetype's binding.

# Archetypes are merged partial manifests, not inherited templates

Archetypes (`archetypes/<name>.py`) contribute partial manifests — dicts of commands, actions, modules, urls — that the generator merges in list order. There is no base template, no `extends`, no override blocks. `archetypes = ["docker", "apple"]` means "merge both dicts, later wins on conflicts."

**Why.** Composability is the load-bearing requirement: real projects mix archetypes (an Apple app that also deploys via docker; a Forge engine project that's also a Rust workspace). A template-inheritance model would force a diamond resolution and require explicit `super()` calls between archetypes that have no inherent ordering relationship. Dict merge is order-explicit at the call site and trivially debuggable — you can print the manifest between merges.

**Considered and rejected.** Jinja-style template inheritance with overridable blocks. Nicer to read in isolation, but blocks `archetypes = [A, B]` from working without each archetype knowing about the other. Also pulls in `jinja2`, which violates [ADR-0001](./0001-stdlib-only.md).

**Consequence.** Conflicts between archetypes are silent (last write wins) — the order in the manifest is meaningful. Validation in `gen/archetypes.py` catches structural errors (a command with `kind`) but not semantic clashes (two archetypes defining `build` differently). If a real clash emerges, the right fix is to rename one side, not introduce inheritance.

**Amendment (admin-mb5q, retire-the-config-tiers round 2).** One archetype is no longer named in any manifest's `archetypes` list: `base` (`archetypes/base/archetype.toml`, Go's `internal/archetype.Resolve`) merges in implicitly, first, before every declared archetype and before the project's own manifest — replacing the old global `~/.config/repo/config.toml` tier's `[[populate]]` patterns now that no config file exists outside `admin.toml`. It is still an ordinary partial manifest under this ADR's merge rule, not a template: a project that lists `base` explicitly gets the identical result (the implicit pass is skipped so the explicit one doesn't double it), and any declared archetype or the project itself still wins on a key `base` also declares, because `base` merges first and "later wins" is unchanged. The only thing implicit about it is that a project's `archetypes` list stays untouched — the point being that no existing manifest needs an edit to keep receiving `base`'s populate patterns.

# Command/action schema validation lives in `admin_lib/validate.py`

All "is this command/action well-formed" checks live in one module, `admin_lib/validate.py`, behind `validate_command` / `validate_action_keys` / `validate_action`. The three pipeline sites that previously each hand-rolled these checks — `manifest.parse` (parse phase), `archetypes.load_archetype` (per-file load), and `archetypes._to_command` (resolve phase) — now delegate to it. After `validate_action` returns, `_to_command` only *builds* the `Command`; it contains no schema raises.

**Why.** The pure-routing rule ([ADR-0003](0003-commands-are-pure-routing.md)) and the action-key/kind/targets/requires checks were duplicated across those three sites with subtly different wording, and the real enforcer was a 208-line nameless `_to_command` that interleaved validation with construction. A reader couldn't find "where an action is validated", and the routing rule was enforced in three places that could drift. Concentrating the rules makes the validator discoverable and the routing rule single-sourced.

**Error type — `ValidationError` umbrella, not one flat class.** `validate.py` defines `ValidationError`; `ManifestError` and `ArchetypeError` are now subclasses of it. `validate_*` raise the caller-supplied phase class via an injected `exc` argument (`ManifestError` at parse, `ArchetypeError` at resolve), and admin-run catches the single `ValidationError` base.

**Considered and rejected.** Collapsing to one literal `ValidationError` raised everywhere, with the phase carried only in the message. Rejected because it (a) discards the parse-vs-resolve phase distinction at the *type* level — useful information — and (b) would re-point ~37 existing tests that assert `ManifestError`/`ArchetypeError`. The subclass-umbrella delivers the same "callers catch one type" goal while preserving phase precision and exact messages (via the `exc`+`lead` parameters), so the migration landed with zero message/type test churn.

**Consequence.** `validate.py` owns the schema vocabulary (`VALID_COMMAND_KEYS`, `VALID_ACTION_KEYS`, `_parse_keys`, `_validate_gp_ints`, `inline_targets`) so it imports only `admin_lib/kinds` and never the parser or resolver — that one-way dependency is what lets `manifest.py` and `archetypes.py` call the validator without an import cycle. The phase-dependent `require_steps` flag on `validate_command` preserves that manifest *overrides* may omit `steps` (they come from the archetype merge) while a final/custom command must declare them.
